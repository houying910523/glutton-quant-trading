# 研究层因子存储与查询实施方案

## 1. 文档目的

这份文档把当前仓库的真实状态和你已经做出的技术选择收成一套**可直接实施**的研究层存储方案。

这份方案回答 5 个问题：

1. 当前已经在 SQLite 里的日线行情，后续是否还要再存一份 Parquet
2. 因子/指标值应该如何存
3. 指标不断增加时，如何避免反复重写全部历史数据
4. 日常按年读取、多股票、多指标研究时，查询层应该怎么组织
5. 结合当前仓库状态，接下来代码和目录应该怎么落地

这份文档是对 [06-数据接入与标准化存储方案](./06-数据接入与标准化存储方案.md)、[10-handoff-当前项目进度与TODO](./10-handoff-当前项目进度与TODO.md)、[12-因子开发评估与选股模块详细设计](./12-因子开发评估与选股模块详细设计.md) 在“研究层因子存储”这个主题上的实现收敛。

## 2. 当前项目的真实起点

结合当前仓库，下面这些事实已经成立：

- 行情主库已经是 `SQLite`
- 默认数据库路径是 `data/system/glutton.db`
- 当前正式表只有：
  - `stock`
  - `trading_calendar`
  - `daily_quote`
  - `ingestion_batch`
- 当前只有 `1d` 日线数据
- 当前研究与回测主线还没有正式实现
- 当前依赖里已经有 `polars`，但还没有 `duckdb`

当前 SQLite 日线表的关键事实如下：

- `daily_quote` 用 `(stock_id, trade_date)` 唯一
- 价格按“整数分”存储
- 成交额 `turnover` 也按“整数分”存储
- `stock` 表里有 `exchange` 和 `symbol`

因此，当前更合理的起点不是把日线行情整体迁出 SQLite，而是：

> **保持 SQLite 继续做标准层行情主库，只把研究层的因子值物化到 Parquet。**

---

## 3. 需求收敛

结合你的使用方式，这个问题的真实需求是：

1. **日线行情不重复存成 Parquet**，继续直接用 SQLite 里的 `daily_quote`
2. **后续要做因子研究**，经常会按年读取很多股票和很多指标
3. **指标会持续增加**，不能因为加一个新指标就把全部已有指标重写一遍
4. **指标要按日更新**，但频率是日级，不是高频逐笔
5. **日常开发要简单**，不能为了“未来可能的平台化”把首版结构做得太重

这几个需求放在一起以后，最重要的设计取舍是：

- SQLite 负责**日更、修数、作为事实来源**
- Parquet 负责**因子物化、低成本存储、分析型读取**
- DuckDB 负责**查询和 join**

---

## 4. 最终方案结论

## 4.1 总体架构

推荐你在当前项目里采用下面这套结构：

```text
SQLite（行情主库）
    +
Parquet（只存因子/指标值）
    +
DuckDB（研究查询层）
```

分工如下：

### SQLite
负责：

- `stock`
- `trading_calendar`
- `daily_quote`
- 日线增量同步
- 历史修复与标准层事实口径

### Parquet
负责：

- 已计算好的技术指标/因子值
- 研究用中间结果的长期保存
- 低成本按列读取

### DuckDB
负责：

- 直接读 Parquet 因子文件
- 直接 attach 当前 SQLite 主库
- 把 SQLite 行情和 Parquet 因子 join 成研究宽表

---

## 4.2 因子存储粒度的最终决定

在当前约束下，不建议：

- 把所有指标都塞到一个大宽表 Parquet 数据集里
- 也不建议先人为区分“核心指标”“扩展指标”再分组管理

结合“指标会不断增加”和“日级更新”的要求，更合适的方案是：

> **一个“因子定义”对应一个 Parquet dataset 目录。**

这里的“因子定义”指的是：

- `indicator_id`
- `version`
- `params`

例如：

- `ma, v1, {window: 5}`
- `ma, v1, {window: 20}`
- `macd, v1, {fast: 12, slow: 26, signal: 9}`
- `boll, v1, {window: 20, num_std: 2}`

每个因子定义各自拥有一套自己的 Parquet dataset。

这样做的好处非常直接：

- 新增一个因子时，只创建一套新目录，不影响其他因子
- 升级一个因子版本时，只创建 `v2`，不改 `v1`
- 日常更新时，只重写当前月这个因子自己的文件
- 你不需要一开始就手动维护“核心指标分层”

这比“一个总大表”更适合你当前的实际工作方式。

---

## 5. 为什么这个方案比“一个大指标表”更适合当前项目

## 5.1 不重复存行情，避免无意义冗余

当前项目已经有稳定的 SQLite 标准层，日线行情完全可以继续直接使用。

如果再把所有行情复制一份到 Parquet：

- 会增加数据冗余
- 会增加同步链路复杂度
- 还要维护两份行情口径一致性

而你的核心矛盾并不在“行情怎么存”，而在“因子怎么存”。

所以首版不需要把 `daily_quote` 再导一份 Parquet。

---

## 5.2 因子会不断增加，不能把 schema 绑死在一个大宽表里

如果把所有指标都放到一个统一的 `indicators/` 宽表数据集中：

- 查起来很方便
- 但每次新增列都会涉及历史分区重写
- 随着指标越来越多，schema 会越来越难维护

而你现在已经明确说了：

- 会持续增加指标
- 日常研究可能会只取其中部分指标

因此，更合理的做法不是做一个“永远正确的大宽表”，而是做：

> **按因子定义拆 dataset，查询时按需 join。**

对日频研究来说，这个 join 成本是可以接受的。

---

## 5.3 日级数据下，按月重写当前因子文件是完全可接受的

因为你现在是日级行情，不是分钟级或 Tick 级。

A 股日线一年大约是：

- 约 240~250 个交易日
- 几千只股票

对于一个单独因子来说，单月数据量并不大。

所以首版完全可以采用一个很实用的策略：

> **因子按 `year/month` 分区，当前月份的文件每天重写一次，历史月份默认只读。**

这样做非常简单：

- 不需要做 Parquet 小文件追加管理
- 不需要先做复杂 compaction
- 不需要先做额外的时序数据库

这正适合个人/小团队日频量化系统。

## 6. 目录与存储布局

## 6.1 新增目录建议

建议在当前项目里新增研究层目录：

```text
data/
  system/
    glutton.db
  raw/
    ...
  research/
    factors/
    duckdb/
      research.duckdb
```

对应含义：

- `data/system/glutton.db`：继续作为标准层 SQLite 主库
- `data/research/factors/`：只存因子 Parquet dataset
- `data/research/duckdb/research.duckdb`：研究查询工作区

---

## 6.2 因子目录结构

建议因子目录统一按下面的模式组织：

```text
data/research/factors/
  {storage_key}/
    year=2024/
      month=01/
        data.parquet
      month=02/
        data.parquet
    year=2025/
      month=01/
        data.parquet
```

其中：

- `storage_key` 由因子定义表提供
- 系统统一约定根目录为 `data/research/factors/{storage_key}`
- 不在定义表里存具体分区文件路径，只存 `storage_key`

例如：

```text
data/research/factors/
  ma/v1/window_5/
    year=2025/month=03/data.parquet

  ma/v1/window_20/
    year=2025/month=03/data.parquet

  macd/v1/fast_12__slow_26__signal_9/
    year=2025/month=03/data.parquet

  boll/v1/window_20__num_std_2/
    year=2025/month=03/data.parquet
```

### 为什么用这种目录结构

因为它天然支持：

- 新增新因子：新增一棵目录
- 升级版本：新增 `v2`
- 调不同参数：新增 `storage_key`
- 按年读取：直接扫对应年份目录
- 回填历史：只重写目标年月分区

## 7. 因子 Parquet 的数据模型

## 7.1 主键设计

因子数据不要使用 SQLite 内部的 `stock_id` 作为长期存储主键。

更推荐统一使用：

- `trade_date`
- `instrument_id`

其中：

- `trade_date`：交易日
- `instrument_id`：推荐使用 `600519.SH`、`000001.SZ` 这种稳定自然键

这样做的原因：

- 不和本地 SQLite 自增 `id` 强耦合
- 即使你以后重建数据库，因子文件仍然能用
- 也更符合研究侧 `DataFrame` 和 `DuckDB` 的使用习惯

---

## 7.2 公共字段约定

每个因子 dataset 的 Parquet 文件都统一至少包含以下列：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `trade_date` | date | 交易日 |
| `instrument_id` | string | 例如 `600519.SH` |
| `factor_version` | string | 例如 `v1` |
| `updated_at` | timestamp | 本次物化时间 |
| `...因子输出列` | double | 一个或多个指标值 |

其中：

- `factor_version` 可以重复写入文件，便于脱离目录单独使用
- `updated_at` 用于追踪这条因子值最后一次物化时间
- 输出列可以是一个，也可以是多个

---

## 7.4 因子定义元信息表

从这一版开始，因子定义不再以 dataset 内部的 `manifest.json` 作为主注册来源，而是统一收口到 SQLite 表：

```text
indicator_definition
```

这张表以“定义信息”为主，同时额外保留一个**轻量运行进度字段** `last_materialized_date`，用于记录当前定义最近一次成功物化到哪个交易日。

### 为什么这里保留一个轻量进度字段

因为这张表的目标仍然主要是两个：

1. 让计算框架根据定义知道如何计算、写到哪里
2. 让研究层或策略层根据定义知道如何读取

同时，日常调度里确实经常需要知道：

- 这个因子最近物化到了哪一天

所以首版可以接受把 **`last_materialized_date` 这个单字段** 放进 `indicator_definition`，用于记录“最近成功物化到哪个交易日”。

但像下面这些更完整的运行态信息，仍然不建议直接塞进定义表：

- 最近一次刷新是否成功
- 本次刷新用了多久
- 本次刷新写了多少行
- 错误信息和失败重试次数

这些如果后续需要，仍然建议单独设计作业日志表。

### 表结构

```sql
CREATE TABLE IF NOT EXISTS indicator_definition (
    id INTEGER PRIMARY KEY,

    indicator_id TEXT NOT NULL,
    version TEXT NOT NULL DEFAULT 'v1',
    indicator_name TEXT NOT NULL,
    category TEXT NOT NULL,
    compute_ref TEXT NOT NULL,
    params TEXT NOT NULL DEFAULT '{}',
    output_columns TEXT NOT NULL,
    storage_key TEXT NOT NULL,
    description TEXT,
    status TEXT NOT NULL DEFAULT 'active',
    last_materialized_date TEXT,

    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL,

    UNIQUE (indicator_id, version),
    UNIQUE (storage_key)
);

CREATE INDEX IF NOT EXISTS idx_indicator_definition_category_status
ON indicator_definition (category, status);
```

### 字段说明

| 字段 | 说明 |
| --- | --- |
| `indicator_id` | 具体可物化的因子 ID，例如 `ma_20`、`macd_12_26_9` |
| `version` | 因子版本，例如 `v1` |
| `indicator_name` | 给人看的名称，例如 `20日均线` |
| `category` | 分类，例如 `trend`、`momentum`、`volatility` |
| `compute_ref` | Python 实现引用，例如 `modules.indicators.builtin.trend:SimpleMovingAverageFactor` |
| `params` | JSON 字符串，保存这条定义的具体参数 |
| `output_columns` | JSON 字符串，保存输出列名列表 |
| `storage_key` | 相对存储标识，例如 `ma/v1/window_20` |
| `description` | 可选说明 |
| `status` | `active / deprecated / disabled` |
| `last_materialized_date` | 最近一次成功物化到的交易日，格式 `YYYY-MM-DD` |

### 为什么这张表已经足够

因为当前项目里，下面这些都已经是固定约定，不需要再存入表里：

- 输入源固定为 SQLite 的 `daily_quote`
- 频率固定为 `1d`
- 存储格式固定为 `Parquet`
- 分区规则固定为 `year/month`
- 读取主键固定为 `trade_date + instrument_id`
- 当前月写入方式固定为“覆盖当前分区”

因此，定义表主要保留真正变化的部分：

- 因子身份
- 计算实现引用
- 参数
- 输出列
- 存储标识
- 最近成功物化日期（轻量进度字段）

#### `ma_20`

indicator_name: 20日均线

## 7.5 代码契约设计

为了让“定义表 + 计算实现 + 读取层”真正闭环，首版建议统一采用下面这套代码契约。

### 7.5.1 固定约定

先固定 5 个系统级约定：

1. 因子输入数据来自 SQLite 行情加载器
2. 因子输入主键固定为 `trade_date + instrument_id`
3. 因子输出主键固定为 `trade_date + instrument_id`
4. Parquet 根目录固定为 `data/research/factors/{storage_key}`
5. 分区路径固定为 `year=YYYY/month=MM/data.parquet`

这样，定义表里就不需要再重复保存这些信息。

### 7.5.2 `IndicatorDefinition`

数据库中的一条定义，进入 Python 后应先被解析成一个强类型对象。

```python
from typing import Any, Literal

from pydantic import BaseModel, ConfigDict, Field


class IndicatorDefinition(BaseModel):
    model_config = ConfigDict(extra="forbid")

    indicator_id: str
    version: str = "v1"
    indicator_name: str
    category: Literal[
        "trend",
        "momentum",
        "volatility",
        "volume",
        "custom",
    ]
    compute_ref: str
    params: dict[str, Any] = Field(default_factory=dict)
    output_columns: list[str]
    storage_key: str
    description: str | None = None
    status: Literal["active", "deprecated", "disabled"] = "active"
    last_materialized_date: str | None = None
```

这个对象的职责是：

> 表示“一个具体可物化因子定义”的元信息，以及一个最小可接受的物化进度字段。

### 7.5.3 `FactorSpec`

真正用于计算调度的输入依赖，不建议直接存到数据库里，而是由因子实现根据参数返回。

```python
from pydantic import BaseModel, ConfigDict, Field


class FactorSpec(BaseModel):
    model_config = ConfigDict(extra="forbid")

    required_columns: list[str] = Field(default_factory=list)
    required_history_bars: int = 0
    output_columns: list[str] = Field(default_factory=list)
```

这样做的好处是：

- `required_columns` 不会和计算实现脱节
- `required_history_bars` 不需要在数据库里重复维护
- 计算框架只要加载实现并绑定参数，就能得到取数窗口

### 7.5.4 `Factor`

每个 `compute_ref` 指向的实现，都要满足统一接口。

```python
from __future__ import annotations

from abc import ABC, abstractmethod
from typing import Any

import polars as pl


class Factor(ABC):
    @abstractmethod
    def spec(self, params: dict[str, Any]) -> FactorSpec: ...

    @abstractmethod
    def compute(
        self,
        frame: pl.DataFrame,
        params: dict[str, Any],
    ) -> pl.DataFrame: ...
```

约束如下：

- `spec(params)` 返回该参数组合下的 `required_columns`、`required_history_bars`、`output_columns`
- `compute(frame, params)` 的输入必须至少包含：
  - `trade_date`
  - `instrument_id`
  - `spec(params).required_columns`
- `compute(frame, params)` 的输出必须至少包含：
  - `trade_date`
  - `instrument_id`
  - `spec(params).output_columns`
- `compute()` 不做 I/O，不直接访问 SQLite，不直接写 Parquet
- `compute()` 不原地修改输入数据

### 7.5.5 `IndicatorDefinitionRepository`

定义表需要一个专门的读取接口，不建议在业务代码里到处裸写 SQL。

```python
from abc import ABC, abstractmethod


class IndicatorDefinitionRepository(ABC):
    @abstractmethod
    def get(self, indicator_id: str, version: str = "v1") -> IndicatorDefinition: ...

    @abstractmethod
    def list_active(self) -> list[IndicatorDefinition]: ...

    @abstractmethod
    def list_by_category(self, category: str) -> list[IndicatorDefinition]: ...
```

这层的职责是：

- 把 SQLite 行中的 `params` 解析成 `dict`
- 把 `output_columns` 解析成 `list[str]`
- 返回上层可直接使用的 `IndicatorDefinition`

### 7.5.6 `compute_ref` 加载约定

建议统一采用 `module_path:ClassName` 形式，例如：

```text
modules.indicators.builtin.trend:SimpleMovingAverageFactor
modules.indicators.builtin.trend:MacdFactor
modules.indicators.builtin.volatility:BollingerBandFactor
```

运行时统一由一个 loader 负责解析：

```python
def load_factor(definition: IndicatorDefinition) -> Factor:
    ...
```

上层不需要关心 `importlib` 的细节。

### 7.5.7 路径解析契约

不在数据库里存完整文件路径，而是统一由 `storage_key` 推导：

```python
from pathlib import Path


def resolve_dataset_root(indicator_root: Path, definition: IndicatorDefinition) -> Path:
    return indicator_root / definition.storage_key


def resolve_partition_path(
    indicator_root: Path,
    definition: IndicatorDefinition,
    *,
    year: int,
    month: int,
) -> Path:
    return (
        indicator_root
        / definition.storage_key
        / f"year={year:04d}"
        / f"month={month:02d}"
        / "data.parquet"
    )
```

这样：

- 计算框架根据定义就知道写到哪里
- 研究层或策略层根据定义就知道去哪里读

### 7.5.8 计算框架如何使用这套契约

计算框架的最小闭环如下：

```text
读取 indicator_definition
-> load_factor(definition)
-> factor.spec(definition.params)
-> 用 required_columns + required_history_bars 从 SQLite 取 bars
-> factor.compute(frame, definition.params)
-> 校验输出列与 definition.output_columns 一致
-> 写入 data/research/factors/{storage_key}/year=YYYY/month=MM/data.parquet
```

### 7.5.9 研究层/策略层如何使用这套契约

读取侧不需要 import 计算实现，只需要：

```text
读取 indicator_definition
-> 拿到 storage_key
-> 拿到 output_columns
-> 推导 dataset root
-> 用 trade_date + instrument_id 做 join
```

也就是说：

- **计算层**依赖 `compute_ref + params`
- **读取层**依赖 `storage_key + output_columns`

这正好满足“同一条定义既能驱动计算，也能驱动读取”的目标。

## 8. SQLite 行情如何接入研究层

## 8.1 不直接在研究代码里裸写 SQL 字符串

建议在研究层新增一个专门的 SQLite 行情加载器，职责只有一个：

> 把 `stock + daily_quote + trading_calendar` 组织成研究可用的 DataFrame。

建议新增：

```text
modules/research/storage/sqlite_market_loader.py
```

建议它至少提供一个接口：

```python
load_daily_bars(
    start_date: date,
    end_date: date,
    instruments: list[str] | None = None,
    columns: list[str] | None = None,
) -> pl.DataFrame
```

输出列建议统一为：

```text
trade_date,
instrument_id,
open,
high,
low,
close,
volume,
turnover
```

其中：

- `instrument_id` 由 `stock.exchange + stock.symbol` 转成研究层稳定标识
- 价格和成交额在 loader 中完成“分 -> 元”的转换
- 输出层统一使用研究语义，不把 SQLite 的整数分口径泄露给因子实现

---

## 8.2 推荐的 DuckDB 行情视图

因为你后面要做研究和 join，建议在 DuckDB 工作区里为 SQLite 行情创建一个统一视图。

示例：

```sql
INSTALL sqlite;
LOAD sqlite;

ATTACH 'data/system/glutton.db' AS market (TYPE SQLITE);

CREATE OR REPLACE VIEW bars_daily AS
SELECT
    CAST(q.trade_date AS DATE) AS trade_date,
    CASE
        WHEN s.exchange = 'SSE' THEN s.symbol || '.SH'
        WHEN s.exchange = 'SZSE' THEN s.symbol || '.SZ'
    END AS instrument_id,
    q.open / 100.0 AS open,
    q.high / 100.0 AS high,
    q.low / 100.0 AS low,
    q.close / 100.0 AS close,
    q.volume AS volume,
    CASE
        WHEN q.turnover IS NULL THEN NULL
        ELSE q.turnover / 100.0
    END AS turnover
FROM market.daily_quote q
JOIN market.stock s
  ON s.id = q.stock_id;
```

这意味着：

- 行情仍然只存在于 SQLite
- DuckDB 只是查询时 attach 这份 SQLite
- 你不需要把 `daily_quote` 预先复制导入 DuckDB

## 9. DuckDB 查询层方案

## 9.1 DuckDB 的角色

在这套方案里，DuckDB 不是主存储。

它只是：

- 研究查询工作区
- Parquet 因子扫描器
- SQLite + Parquet 的 join 层

建议工作区文件固定为：

```text
data/research/duckdb/research.duckdb
```

## 9.2 因子视图的建议组织方式

对于常用因子，可以在 DuckDB 中建立命名清晰的 view。

例如：

```sql
CREATE OR REPLACE VIEW f_ma_20 AS
SELECT *
FROM read_parquet(
  'data/research/factors/ma/v1/window_20/year=*/month=*/data.parquet'
);

CREATE OR REPLACE VIEW f_macd_12_26_9 AS
SELECT *
FROM read_parquet(
  'data/research/factors/macd/v1/fast_12__slow_26__signal_9/year=*/month=*/data.parquet'
);
```

这样后面研究查询就会很直接。

## 9.3 研究查询示例

### 查询某只股票一年的行情 + MA20 + MACD

```sql
SELECT
    b.trade_date,
    b.instrument_id,
    b.close,
    ma.ma_20,
    m.macd_dif_12_26_9,
    m.macd_dea_12_26_9,
    m.macd_hist_12_26_9
FROM bars_daily b
LEFT JOIN f_ma_20 ma
  USING (trade_date, instrument_id)
LEFT JOIN f_macd_12_26_9 m
  USING (trade_date, instrument_id)
WHERE b.instrument_id = '600519.SH'
  AND b.trade_date BETWEEN DATE '2024-01-01' AND DATE '2024-12-31'
ORDER BY b.trade_date;
```

### 查询某一年全市场某几个指标

```sql
SELECT
    b.trade_date,
    b.instrument_id,
    ma.ma_20,
    boll.boll_upper_20_2,
    boll.boll_lower_20_2
FROM bars_daily b
LEFT JOIN f_ma_20 ma
  USING (trade_date, instrument_id)
LEFT JOIN read_parquet(
  'data/research/factors/boll/v1/window_20__num_std_2/year=2024/month=*/data.parquet'
) boll
  USING (trade_date, instrument_id)
WHERE b.trade_date BETWEEN DATE '2024-01-01' AND DATE '2024-12-31';
```

这类查询正是 DuckDB 的强项。

## 10. 因子日更方案

## 10.1 日更总体原则

因子更新不直接逐条 append 到 Parquet。

首版采用更简单的方式：

> **按月分区；对于当前月份，重新计算并覆盖当月文件。**

这是当前项目最实用的做法。

原因：

- 日线数据量可控
- Parquet 不适合原地 update
- 每天只重写“当前月 + 当前因子”的一个文件，成本很低
- 比“先写小文件再定期 compact”更简单

---

## 10.2 日更流程

建议每日流程如下：

```text
1. 先执行 sync_daily_quotes，把当日行情写入 SQLite
2. 读取 trading_calendar，确定本次研究层目标截止日 target_end
3. 从 indicator_definition 表中取出 status = active 的定义
4. 对每个因子定义：
   4.1 用 compute_ref 加载因子实现
   4.2 用 factor.spec(params) 解析 required_columns 和 required_history_bars
   4.3 从 SQLite 取历史 bars
   4.4 运行因子计算
   4.5 校验输出列与 definition.output_columns 一致
   4.6 过滤出当月数据
   4.7 覆盖写入 data/research/factors/{storage_key}/year=YYYY/month=MM/data.parquet
   4.8 成功后回写 indicator_definition.last_materialized_date
```

这里允许在 `indicator_definition` 表里回写一个轻量进度字段 `last_materialized_date`。

但更完整的运行态，例如成功/失败、耗时、错误信息、写入行数等，仍然建议后续单独做作业日志表。

---

## 10.3 窗口计算规则

每个因子都应该声明：

- `required_columns`
- `required_history_bars`

例如：

- `ma_20` 需要 `close` 和 `20` 个 bar
- `boll_20_2` 需要 `close` 和 `20` 个 bar
- `macd 12,26,9` 虽然理论窗口更复杂，但工程上可以声明一个保守值，例如 `60`

对于当前月文件的重算：

- 月文件实际输出只包含本月数据
- 但输入需要从“本月第一个交易日前的若干交易日”开始拉取

例如：

- 目标重写 `2025-03`
- 因子需要 `required_history_bars = 60`
- 那么实际 SQL 取数窗口是：
  - `2025-03-01` 之前回溯 60 个交易日
  - 一直到 `target_end`

这样才能保证月初的指标值计算正确。

---

## 10.4 Warmup 与缺失值约定

因子 Parquet 文件中允许存在 `NULL`。

典型情况：

- 股票上市不久，历史窗口不足
- 某些价格列缺失
- 某只股票在某段时间没有可用数据

首版约定：

- **保留该行，因子值写 `NULL`**
- 不在物化阶段偷偷丢行
- 后续研究/回测由上层明确决定如何处理缺失值

这样行为最透明。

## 11. 新增因子、升级因子和修历史的处理方式

## 11.1 新增一个因子

例如你新增 `rsi_14`：

- 在 `indicator_definition` 表中插入一条新定义
- `compute_ref` 指向 `RsiFactor` 实现
- `storage_key` 设为：

```text
rsi/v1/window_14
```

- 最终 dataset root 会被解析为：

```text
data/research/factors/rsi/v1/window_14/
```

- 按历史月份回填它自己的 dataset
- 不需要动 `ma`、`macd`、`boll` 任何已有文件

这正是本方案最重要的收益之一。

---

## 11.2 因子算法变更

如果 `macd` 算法实现调整了，不要覆盖原有 `v1`。

直接新增新的定义和新的 `storage_key`，例如：

```text
macd/v2/fast_12__slow_26__signal_9
```

对应 dataset root 为：

```text
data/research/factors/macd/v2/fast_12__slow_26__signal_9/
```

这样：

- 老研究仍然可以复现
- 新研究可以逐步切换到 `v2`
- DuckDB 里按 view 名区分即可

---

## 11.3 历史行情修复后的因子重刷

如果 SQLite 中某段历史行情被修复：

- 不需要全量删除所有因子
- 只需要找出受影响月份
- 对受影响的因子定义重写对应月份分区

建议支持一个 `refresh` 模式：

```text
refresh indicator_id=macd version=v1 start=2024-01-01 end=2024-03-31
```

然后按月份重刷：

- `2024-01`
- `2024-02`
- `2024-03`

即可。

## 15. 这套方案的明确边界

这套方案当前明确不做：

- 把 `daily_quote` 全量复制成 Parquet
- 把所有因子值灌进 SQLite 关系表
- 因子在线实时计算服务
- 高频因子增量流处理
- 指标平台式权限与治理系统

一句话说：

> 这是一套面向当前仓库、面向日频研究、面向个人/小团队的“轻量研究层因子存储方案”，不是大规模因子平台方案。

---

## 16. 最终结论

结合当前项目状态，你最适合的落地方案是：

> **继续让 SQLite 作为日线行情主库；在同一 SQLite 中增加 `indicator_definition` 元信息表；不要把 bars 再导成 Parquet；因子值按“一个因子定义一个 Parquet dataset”存储；按 `year/month` 分区；当前月每日覆盖重写；DuckDB 作为 SQLite + Parquet 的统一查询层。**

这套方案的好处是：

- **和当前仓库现状完全兼容**
- **不重复存行情**
- **新增因子时不需要重写全部已有因子**
- **按年读取、多股票、多指标研究时足够高效**
- **复杂度可控，能直接开始实现**

如果后续因子种类很多、团队规模上来、查询模式进一步复杂，再考虑把这套方案升级为：

- Parquet + DuckDB 数据湖查询
- 或者 Parquet + ClickHouse 的平台化架构

但在当前阶段，没有必要一步走到那一步。
