# 策略接口与回测接口设计

## 1. 目标

这份文档只定义首版 MVP 中两类接口：

1. 策略接口
2. 回测接口

它们共同服务于当前最小闭环：

```text
标准化数据 -> 策略生成信号 -> 回测引擎解释信号 -> 输出回测结果
```

## 2. 非目标

这份文档明确不覆盖：

- 订单接口
- 账户与持仓接口
- 组合构建模块接口
- 风险控制模块接口
- 模拟盘与实盘执行接口

这些能力属于下一阶段，不应提前混进首版设计。

## 3. 首版默认假设

为避免实现时再拍脑袋，首版直接锁定以下默认值：

- 数据频率：`1d`
- 市场示例：A 股
- 交易方向：`long_only`
- 信号类型：选股/排序信号
- 回测调仓：按固定频率重平衡
- 内置持仓规则：`top_n + 等权`
- 默认成交假设：`next_open`

这里最关键的一点是：

> 首版策略只负责“告诉系统哪些标的值得持有”，不负责“具体持仓怎么分”。

首版不单独设计组合构建接口，回测引擎内部使用一个最小且固定的持仓规则来解释信号。

补充约定：

- 这份文档里的应用层接口对象使用 `camelCase`
- 落库字段仍以 [05-数据模型设计](./05-数据模型设计.md) 中的 `snake_case` 为准
- 两者之间允许存在一层明确的字段映射，不允许靠隐式约定混用

## 4. 为什么策略接口按“日期切片”设计

对于股票量化，很多策略不是对单只股票逐条事件处理，而是在某个交易日对一组股票做横截面比较，例如：

- 选出涨幅前 20 的股票
- 选出成交额满足阈值且均线向上的股票
- 对一组股票按打分排序

因此首版策略接口不做 `on_bar(bar)` 这种逐条回调，而是做成：

```text
给定一个交易日和这一日的候选股票数据
-> 返回当日信号列表
```

这样更贴合当前 MVP，也更适合后续扩展成周频、月频再平衡策略。

## 5. 策略接口设计

## 5.1 公开对象

### StrategyManifest

表示一个策略的静态元信息。

```ts
interface StrategyManifest {
  strategyId: string;
  strategyName: string;
  version: string;
  description?: string;
  barFrequency: "1d";
  longOnly: true;
  defaultParams: Record<string, unknown>;
}
```

### StrategyInputRow

表示策略在某个交易日看到的一条标的数据。

```ts
interface StrategyInputRow {
  instrumentId: string;
  tradeDate: string;
  bar: {
    open: number;
    high: number;
    low: number;
    close: number;
    volume: number;
    turnover?: number;
  };
  history?: Array<{
    tradeDate: string;
    open: number;
    high: number;
    low: number;
    close: number;
    volume: number;
    turnover?: number;
  }>;
  features?: Record<string, number | string | boolean | null>;
}
```

说明：

- `bar` 是当前交易日数据
- `history` 是回测引擎根据窗口长度预先切好的历史序列
- `features` 是可选衍生特征，但首版不强制

### StrategyInput

表示某个交易日的完整策略输入。

```ts
interface StrategyInput {
  tradeDate: string;
  datasetSpecId: string;
  params: Record<string, unknown>;
  rows: StrategyInputRow[];
}
```

### SignalRecord

表示策略生成的一条信号。

```ts
interface SignalRecord {
  instrumentId: string;
  tradeDate: string;
  signalSide: "long" | "flat";
  score: number;
  reason?: string;
}
```

说明：

- `signalSide` 首版只允许 `long` 或 `flat`
- `score` 用于排序，越大代表越应该被选中
- `reason` 只做调试和复盘辅助，不参与引擎逻辑

### StrategyOutput

```ts
interface StrategyOutput {
  tradeDate: string;
  signals: SignalRecord[];
}
```

## 5.2 公开接口

首版策略接口保持极简，只定义 3 个方法。

```ts
interface Strategy {
  manifest(): StrategyManifest;
  validateParams(params: Record<string, unknown>): void;
  generateSignals(input: StrategyInput): StrategyOutput;
}
```

### `manifest()`

职责：

- 返回策略元信息
- 暴露默认参数
- 标识策略版本

### `validateParams(params)`

职责：

- 校验参数是否齐全
- 校验参数类型和取值范围
- 在参数错误时直接抛出错误

首版要求：

- 不返回复杂验证对象
- 校验失败直接失败，不做容错修复

### `generateSignals(input)`

职责：

- 读取某个交易日的候选标的数据
- 生成当日信号列表

约束：

- 纯函数风格，不做外部 I/O
- 不直接读数据库
- 不直接写文件
- 不依赖全局可变状态
- 同样的输入必须产生同样的输出

## 5.3 策略接口的实现约束

为了保证回测可复现，策略实现必须遵守以下约束：

- 不允许在策略里直接发 HTTP 请求
- 不允许在策略里临时查询数据库
- 不允许读取系统当前时间决定信号
- 不允许修改输入对象
- 不允许把仓位控制逻辑伪装成信号接口的一部分

## 5.4 一个最小示例

下面这个例子表达的是“按过去 20 日收益率排序，选最强的一批股票”。

```ts
class Momentum20Strategy implements Strategy {
  manifest(): StrategyManifest {
    return {
      strategyId: "momentum_20",
      strategyName: "20日动量",
      version: "v1",
      barFrequency: "1d",
      longOnly: true,
      defaultParams: { lookbackDays: 20, minHistoryDays: 20 }
    };
  }

  validateParams(params: Record<string, unknown>): void {
    if (typeof params.lookbackDays !== "number") {
      throw new Error("lookbackDays must be a number");
    }
  }

  generateSignals(input: StrategyInput): StrategyOutput {
    const signals = input.rows
      .filter((row) => (row.history?.length ?? 0) >= 20)
      .map((row) => {
        const first = row.history![0].close;
        const last = row.bar.close;
        const score = (last - first) / first;
        return {
          instrumentId: row.instrumentId,
          tradeDate: input.tradeDate,
          signalSide: "long" as const,
          score
        };
      });

    return { tradeDate: input.tradeDate, signals };
  }
}
```

## 6. 回测接口设计

## 6.1 设计原则

因为首版没有单独的组合构建模块，回测引擎必须内置一个最小持仓解释规则。

这个规则固定为：

1. 从策略输出中筛选 `signalSide = long`
2. 按 `score` 从高到低排序
3. 取前 `maxPositions`
4. 等权分配
5. 按再平衡频率更新持仓

这不是在偷偷加入组合模块，而是在没有组合模块之前，为了让信号可以被回测而采用的最小固定规则。

## 6.2 公开对象

### BacktestRequest

```ts
interface BacktestRequest {
  id: string;
  strategyId: string;
  strategyVersion: string;
  datasetSpecId: string;
  params: Record<string, unknown>;
  startDate?: string;
  endDate?: string;
  initialCapital: number;
  rebalanceFrequency: "daily" | "weekly" | "monthly";
  maxPositions: number;
  executionPrice: "next_open" | "same_close";
  commissionBps: number;
  slippageBps: number;
  longOnly: true;
}
```

说明：

- `startDate` / `endDate` 为空时，默认使用数据集全量区间
- `same_close` 只允许用于研究对照，不推荐作为默认成交假设
- `next_open` 是首版推荐默认值，用来避免明显前视偏差

### BacktestResultPayload

这个对象与当前数据模型里的 `BacktestResult` 对齐。

```ts
interface BacktestResultPayload {
  id: string;
  strategyId: string;
  strategyVersion: string;
  datasetSpecId: string;
  params: Record<string, unknown>;
  startedAt: string;
  finishedAt?: string;
  status: "running" | "success" | "failed";
  errorMessage?: string;
  totalReturn?: number;
  annualReturn?: number;
  maxDrawdown?: number;
  sharpe?: number;
  tradeCount?: number;
  winRate?: number;
}
```

## 6.3 公开接口

```ts
interface BacktestEngine {
  run(request: BacktestRequest, strategy: Strategy): BacktestResultPayload;
}
```

首版只保留同步接口，不设计任务队列接口。

原因很简单：

- 当前回测规模不大
- 当前没有异步任务中心
- 先把结果算对，比先把任务跑得花哨更重要

## 6.4 回测执行流程

回测引擎固定按以下顺序运行：

1. 读取 `datasetSpecId` 对应的数据集定义
2. 裁剪回测区间
3. 按交易日历生成回测日期序列
4. 对每个再平衡日构造 `StrategyInput`
5. 调用 `strategy.generateSignals`
6. 校验信号格式是否合法
7. 按内置规则选出 `top_n` 持仓
8. 按成交假设计算下一周期收益
9. 扣减手续费和滑点
10. 聚合指标并写出 `BacktestResult`

## 6.5 回测引擎必须做的校验

### 请求校验

- `id` 不得为空
- `datasetSpecId` 必须存在
- `maxPositions` 必须大于 0
- `initialCapital` 必须大于 0
- `commissionBps`、`slippageBps` 不得为负
- `longOnly` 首版必须为 `true`

### 信号校验

- `instrumentId` 必须在数据集中存在
- `tradeDate` 必须等于当前回测交易日
- `signalSide` 只能是 `long` 或 `flat`
- `score` 必须是数值
- 同一交易日、同一标的不允许重复信号

### 数据校验

- 回测日期必须来自交易日历
- 产生信号的标的必须在该交易日存在行情
- 如果 `executionPrice = next_open`，则下一交易日必须存在可用价格

## 6.6 指标口径

首版回测结果至少输出以下指标：

- `total_return`
- `annual_return`
- `max_drawdown`
- `sharpe`
- `trade_count`
- `win_rate`

口径要求：

- 所有指标只基于同一次 `BacktestRequest`
- 指标结果只写入一张 `backtest_result` 表
- 更细的权益曲线、每日持仓、信号明细暂不建正式表

## 6.7 错误处理

首版错误处理保持简单直接：

- 参数错误：直接失败
- 数据缺失：直接失败
- 策略抛错：直接失败
- 结果写入失败：直接失败

失败时至少要保证：

- `status = failed`
- `errorMessage` 有值
- 已有的原始输入数据不被修改

## 7. 接口边界总结

为了防止后面实现时边界漂移，这里把职责再钉一次：

### 策略接口负责

- 根据输入数据生成信号
- 定义策略参数
- 校验策略参数

### 回测接口负责

- 加载数据集
- 组织时间轴
- 调用策略
- 用固定规则把信号转成持仓
- 计算收益与指标
- 持久化回测结果

### 当前明确不负责

- 自定义下单逻辑
- 自定义订单状态机
- 资金冻结与账户同步
- 复杂组合优化
- 风险插件系统

## 8. 首版测试场景

这份接口设计至少要支持以下测试场景：

1. 参数合法的简单动量策略可以稳定返回信号
2. 参数缺失时 `validateParams` 直接失败
3. 同一数据集上重复回测，结果一致
4. 非交易日不会调用策略生成信号
5. `next_open` 模式下缺少下一交易日价格时，回测直接失败
6. 同一标的同一日重复信号时，回测直接失败
7. `maxPositions = 5` 时，引擎只保留分数最高的 5 个标的

## 9. 对后续演进的预留

这套接口故意留得很窄。等进入下一阶段后，再考虑扩展：

- 组合构建接口
- 风险过滤接口
- 异步回测任务接口
- 回测明细产物接口
- 模拟盘/实盘统一策略运行时接口

在进入这些阶段之前，不要提前把当前接口做成抽象工厂或插件系统。
