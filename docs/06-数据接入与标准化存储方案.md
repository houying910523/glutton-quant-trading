# 数据接入与标准化存储方案

## 1. 目标

这份文档描述当前首版数据底座的实现方案。

当前方案只回答两件事：

1. 数据如何接入
2. 接入后的标准数据如何存储

它不讨论策略、回测、订单和实盘。

## 2. 当前范围

当前实现只接 3 类数据：

- 标的基础信息
- 交易日历
- 日线行情

当前不接：

- Tick
- L2
- 实时推送流
- 新闻公告
- 券商账户数据

## 3. 当前总体流程

当前主链路可以概括为：

```text
AkShare
-> 资源级 adapter
-> pipeline 创建批次
-> Raw manifest 落盘
-> 标准化为 Pydantic 记录对象
-> SQLite upsert
-> 更新批次统计
```

当前实现里：

- Raw Layer 默认只写 `manifest.json`
- Standard Layer 是 SQLite
- Serving Layer 还没有正式实现

## 4. 当前数据源策略

当前代码只支持一个程序化主数据源：

- `AkShare`

虽然类型定义里还保留了 `"tushare"`，但当前 factory 并没有实现对应 adapter。

这意味着当前真实策略是：

- 不做多源仲裁
- 不做主备切换
- 不做自动 fallback

## 5. 当前 adapter 设计

当前实现没有采用“统一 request -> 统一 raw record”的总接口，而是按资源拆成 3 类 fetcher：

- `StockFetcher.fetch()`
- `TradingCalendarFetcher.fetch(start_date, end_date)`
- `StockDailyQuoteFetcher.fetch(symbol, start_date, end_date, stock_id, batch_id)`

这样做的原因很直接：

- 股票列表是全量快照
- 交易日历是区间展开
- 日线行情是单股票区间抓取

三类资源的抓取参数并不相同，硬合并接口只会增加无意义抽象。

## 6. 当前批次方案

所有同步任务都通过 `ingestion_batch` 记录批次。

当前正式字段以数据库为准，核心包括：

- `batch_key`
- `source_name`
- `resource_type`
- `sync_mode`
- `start_date`
- `end_date`
- `request_params`
- `status`
- `raw_count`
- `valid_count`
- `loaded_count`
- `rejected_count`
- `error_summary`

当前批次状态流转是：

```text
pending -> running -> success/failed
```

当前已实现：

- 批次创建
- 运行中标记
- 成功/失败完成
- 重试次数统计

当前未实现：

- 完整请求参数回填
- 覆盖率告警关联
- 批次级质量问题查询链路

## 7. 当前任务拆分

当前 CLI 任务已经拆成 3 个：

1. `sync_stocks`
2. `sync_trading_calendar`
3. `sync_daily_quotes`

它们分别对应：

- 股票基础信息全量同步
- 交易日历区间同步
- 个股日线增量同步

## 8. 当前标准化方案

## 8.1 `Stock`

当前标准化结果是 `StockRecord`，核心约定：

- `market = CN`
- `exchange in {SSE, SZSE}`
- `asset_type = stock`
- `currency = CNY`
- `lot_size = 100`

## 8.2 `TradingCalendar`

当前标准化结果是 `TradingCalendarRecord`，核心约定：

- 在 pipeline 中对自然日区间逐天展开
- 在 adapter 返回的开市日集合里则 `is_open = true`
- 否则 `is_open = false`

## 8.3 `DailyQuote`

当前标准化结果是 `DailyQuoteRecord`，核心约定：

- `open/high/low/close` 存整数分
- `volume` 存整数股
- `turnover` 存整数分
- `stock_id` 和 `ingestion_batch_id` 在 pipeline 阶段注入

## 9. 当前质量校验

当前已经落地的质量校验是最小版本：

- `Pydantic` 模型校验
- SQLite 唯一键约束
- SQLite 外键约束
- SQLite 的 OHLC 合法性约束

当前没有正式落地的能力：

- `data_quality_issue` 表
- `warn/reject` 分级质量问题记录
- `daily_quote` 覆盖率阈值告警
- 历史缺口自动拦截

## 10. 当前存储分层

## 10.1 Raw Layer

当前实现状态：

- 已有目录组织
- 已写 `manifest.json`
- `records.jsonl` 仅有 helper，默认流程未写入

## 10.2 Standard Layer

当前已正式落地：

- `stock`
- `trading_calendar`
- `daily_quote`
- `ingestion_batch`

## 10.3 Serving Layer

当前未实现。

回测和研究未来会读取标准层，但当前代码还没有进入这一步。

## 11. 当前同步行为约定

### 股票基础信息

- 当前按全量快照同步

### 交易日历

- 当前必须显式提供 `start_date` 和 `end_date`

### 日线行情

- 当前按股票增量续跑
- 如果本地已有历史，则从该股票最新落库日期的下一天开始
- 如果本地没有历史，则从 `listed_at` 或默认起点 `1991-01-01` 开始
- 同步终点取本地交易日历中不晚于今天的最后一个开市日

## 12. 当前方案结论

当前数据方案不是一个“大而全的数据平台”，而是一版很收敛的本地离线实现：

> 用 AkShare 拉股票、日历和个股日线，把结果通过 Python pipeline 落到 SQLite，并用批次表跟踪同步过程；先保证主链路跑通，再逐步补原始记录、质量问题和回测读取能力。
