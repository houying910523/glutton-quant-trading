# 研究层指标存储与刷新方案

## 1. 文档目的

这份文档只描述当前代码里**已经落地**的指标定义、刷新、存储和查询方案。

基准文件：

- `modules/indicators/`
- `modules/repositories/indicator_repository.py`
- `modules/datasource/service/stock_daily_service.py`
- `sql/002_indicators.sql`
- `sql/003_initial_builtin_indicator.sql`

它回答 5 个问题：

1. 指标定义放在哪里
2. 指标值落在哪里
3. 刷新脚本如何工作
4. 查询服务如何拼接多个指标数据集
5. 当前哪些能力还没做

## 2. 当前实现结论

当前仓库里的指标层已经形成下面这套结构：

```text
SQLite（指标定义元数据）
    +
Parquet（指标值年度分区）
    +
DuckDB（查询时临时拼接多个分区）
```

分工如下：

### SQLite

负责保存：

- 指标标识与版本
- 计算实现 `compute_ref`
- 参数 `params`
- 输出列 `output_columns`
- 存储路径 `storage_key`
- 启停状态 `status`
- 最近物化进度 `last_materialized_date`

对应表：

- `indicators`

默认路径：

- `data/system/glutton.db`

### Parquet

负责保存：

- 指标值结果集
- 按 `storage_key` 隔离的数据集目录
- 按年分区的持久化文件

默认根目录：

- `data/indicators`

### DuckDB

负责：

- 查询时读取多个 Parquet 分区
- 以 `trade_date + instrument_id` 为键做拼接
- 给 `IndicatorController` 返回统一结果集

当前实现方式：

- 不是单独的常驻查询服务
- 而是在 `IndicatorService` 内使用内存 DuckDB 临时查询

## 3. 指标定义模型

### 3.1 持久化层：`IndicatorRecord`

位置：`modules/repositories/models.py`

对应表：`indicators`

核心字段：

- `indicator_id`
- `version`
- `indicator_name`
- `category`
- `compute_ref`
- `params`
- `output_columns`
- `storage_key`
- `status`
- `last_materialized_date`
- `attach_kline`

当前约束：

- `(indicator_id, version)` 唯一
- `storage_key` 唯一

### 3.2 运行时层：`IndicatorDefinition`

位置：`modules/indicators/models.py`

用途：

- 把 `IndicatorRecord` 映射成指标刷新时使用的运行时对象
- 供 `load_indicator()` 动态加载具体实现类

### 3.3 规格层：`IndicatorSpec`

位置：`modules/indicators/models.py`

由具体指标实现返回，用于声明：

- `required_columns`
- `required_history_bars`
- `output_columns`

这决定了刷新脚本该从 `stock_daily` 取哪些列，以及要为窗口型指标额外回看多少历史。

## 4. 指标实现与内置能力

### 4.1 抽象协议

位置：`modules/indicators/base.py`

当前抽象：

```python
class Indicator(ABC):
    def spec(self, params: dict[str, Any]) -> IndicatorSpec: ...
    def compute(self, frame: pl.DataFrame, params: dict[str, Any]) -> pl.DataFrame: ...
```

### 4.2 动态加载

`load_indicator(definition)` 会按 `compute_ref` 解析：

```text
module.path:ClassName
```

并返回具体 `Indicator` 实例。

### 4.3 当前内置指标

位置：`modules/indicators/builtin/`

当前已实现：

- `SimpleMovingAverageIndicator`
- `MacdIndicator`
- `BollingerBandIndicator`
- `AverageTrueRangeIndicator`

对应种子数据位于：

- `sql/003_initial_builtin_indicator.sql`

## 5. 指标存储组织方式

当前规则是：

> 一个 `storage_key` 对应一个 Parquet 数据集目录。

目录结构如下：

```text
data/indicators/{storage_key}/
  year=2024/
    data.parquet
  year=2025/
    data.parquet
```

由以下模块负责路径与读写：

- `modules/indicators/storage/path_resolver.py`
- `modules/indicators/storage/indicator_store.py`

### 5.1 路径规则

- `resolve_dataset_root(indicator_root, storage_key)`
- `resolve_partition_path(indicator_root, storage_key, year=YYYY)`
- `resolve_partition_glob(indicator_root, storage_key)`

### 5.2 写入规则

`IndicatorStore.write_year_partition()` 会：

- 确保父目录存在
- 把 `trade_date` 规范化为字符串后写 parquet
- 固定覆盖对应年分区文件

### 5.3 读取规则

`IndicatorStore.read_year_partition()` / `read_dataset()` 会：

- 读回 parquet
- 将字符串 `trade_date` 恢复为 `pl.Date`

## 6. 当前刷新链路

入口：

- `modules/indicators/scripts/refresh_indicators.py`

主链路如下：

```text
读取 indicators 中 active 定义
-> 转成 IndicatorDefinition
-> load_indicator()
-> 读取 spec.required_columns / spec.required_history_bars
-> StockDailyService.load_stock_daily()
-> Indicator.compute()
-> 规范化输出列
-> 写入 data/indicators/{storage_key}/year=YYYY/data.parquet
-> 更新 last_materialized_date
```

关键协作件：

- `modules/indicators/base.py`：`Indicator` 抽象与 `load_indicator()`
- `modules/indicators/models.py`：`IndicatorDefinition`、`IndicatorSpec`
- `modules/datasource/service/stock_daily_service.py`：从 SQLite 读取标准层日线
- `modules/indicators/storage/indicator_store.py`：Parquet 分区读写
- `modules/repositories/indicator_repository.py`：管理 `indicators` 表

## 7. 当前刷新粒度与增量策略

### 7.1 以“年”为分区粒度

刷新时会把目标区间拆成若干年度片段：

- `2024-01-01 ~ 2024-12-31`
- `2025-01-01 ~ 2025-12-31`
- ...

### 7.2 以 `last_materialized_date` 推进起点

默认行为：

- 若定义里没有 `last_materialized_date`，从传入 `start_date` 开始
- 若已有进度，且没开 `force`，会从已物化日期之后继续
- 若 `force = true`，忽略已有进度，按传入区间重算

### 7.3 为窗口型指标补历史

刷新某个年度片段时，不是只读分区内日期，而是会额外向前补历史窗口：

```text
load_start = partition_start_date - history_padding_days(spec)
```

这样即使重算的是年内后半段，均线、ATR、MACD 等窗口型指标也能拿到足够上下文。

### 7.4 年内部分重算会合并旧分区

如果本次重算只覆盖某年中的一部分日期：

- 会先读取原有年份分区
- 再把新结果按 `trade_date + instrument_id` 去重覆盖
- 最终整年重写该分区文件

## 8. 当前查询链路

入口：

- `modules/indicators/indicator_service.py`
- HTTP 暴露：`IndicatorController.get_indicator_detail()`

查询过程如下：

```text
传入 stock_id + 日期区间 + 指标列名列表
-> 从 stock_info 解析 instrument_id
-> 从 indicators 中找出这些列归属的 active 指标定义
-> 过滤掉本地尚未存在 parquet 数据集的定义
-> DuckDB read_parquet(year=*/data.parquet)
-> 对多个指标数据集做 FULL OUTER JOIN
-> 补齐缺失列并按 trade_date 排序返回
```

当前查询特征：

- 查询粒度是**单股票 + 多指标列**
- 输入的 `names` 对应的是 `output_columns`，不是 `indicator_id`
- 若某列没有找到对应定义，直接忽略
- 若数据集目录不存在，直接跳过
- 缺失列会补成 `NULL`

## 9. 当前已实现的指标能力

当前指标层已经不只是“设计稿”，而是完整打通了最小闭环：

- `indicators` 表和 repository
- 内置指标实现
- 指标定义到运行时定义的映射
- 从 SQLite 读取标准层日线
- 指标计算并按年写入 Parquet
- 基于 DuckDB 的查询拼接
- 对应单元测试

换句话说，当前研究侧最稳定的部分之一就是：

> 指标定义 + 指标物化 + 指标查询

## 10. 当前没有做的部分

这套方案当前还没有覆盖：

- 指标结果回写 SQLite 元数据索引表以外的更多查询加速结构
- 多股票横截面统一查询服务
- 因子评估结果落盘
- 标签结果落盘
- 宽表导出工作区
- 回测结果与指标数据的一体化查询
- `attach_kline` 的正式使用语义

## 11. 当前结论

结合当前仓库状态，研究侧指标层最准确的描述是：

> `indicators` 表负责定义和进度；`data/indicators/{storage_key}/year=YYYY/data.parquet` 负责持久化指标值；DuckDB 负责查询时的临时拼接。

因此，当前指标层的准确描述是：

> `indicators` 表负责定义和进度；`data/indicators/{storage_key}/year=YYYY/data.parquet` 负责持久化指标值；DuckDB 负责查询时的临时拼接。
