# 研究层指标存储与刷新方案

## 1. 文档目的

这份文档只保留当前代码已经落地的研究侧指标存储方案，不再展开 DuckDB 工作区、额外查询层或未来目录草案。

它回答 4 个问题：

1. 标准层行情和研究侧指标分别存在哪里
2. 一个指标定义如何映射成一个可刷新的数据集
3. 当前指标刷新脚本怎么工作
4. 当前还没有做哪些能力

## 2. 当前实现结论

当前仓库已经收敛出的结构是：

```text
SQLite（标准层行情主库）
    +
Parquet（研究侧指标分区文件）
```

分工如下：

### SQLite

负责：

- `stock`
- `trading_calendar`
- `daily_quote`
- `ingestion_batch`
- `indicator_definition`

默认路径：

- `data/system/glutton.db`

### Parquet

负责：

- 指标值长期落盘
- 按指标定义隔离存储
- 按月分区更新

默认根目录：

- `data/indicators`

当前没有实现 DuckDB，也没有单独的研究查询工作区。

## 3. 为什么当前不重复存行情

当前标准层日线已经能稳定从 SQLite 读取：

- `daily_quote` 以 `(stock_id, trade_date)` 唯一
- 价格按整数分存储
- `stock` 能补齐 `exchange`、`symbol` 等维度

因此当前更合理的取舍是：

> 继续让 SQLite 作为标准层事实来源，只把研究侧指标物化到 Parquet。

这样可以避免：

- 行情双写
- 两份历史口径不一致
- 为了研究而提前引入额外查询基础设施

## 4. 指标数据集的组织方式

当前采用的规则是：

> 一个 `indicator_definition` 对应一个 Parquet 数据集目录。

`indicator_definition` 当前至少包含：

- `indicator_id`
- `version`
- `params`
- `compute_ref`
- `output_columns`
- `storage_key`
- `last_materialized_date`

其中真正决定落盘路径的是：

- `storage_key`

目录结构如下：

```text
data/indicators/{storage_key}/
  year=2025/
    month=01/
      data.parquet
    month=02/
      data.parquet
```

这种方式的好处是：

- 新增指标不会改已有指标目录
- 升级指标版本不会覆盖旧版本
- 按月重写时只影响当前指标自己的分区

## 5. 当前刷新链路

当前入口在：

- `modules/indicators/scripts/refresh_indicators.py`

主链路可以概括为：

```text
读取 indicator_definition
-> 选择 active 指标
-> 解析 compute_ref 并加载 Indicator 实现
-> 从 StockDailyService 读取所需日线窗口
-> 调用 Indicator.compute()
-> 规范化输出列
-> 写入月分区 Parquet
-> 更新 last_materialized_date
```

当前实现里的关键协作件：

- `modules/indicators/base.py`：`Indicator` 抽象与 `load_factor()`
- `modules/indicators/models.py`：`IndicatorDefinition`、`IndicatorSpec`
- `modules/indicators/storage/indicator_store.py`：按月分区读写
- `modules/datasource/service/stock_daily_service.py`：从标准层读取日线
- `modules/repositories/indicator_definition_repository.py`：管理指标定义

## 6. 当前更新粒度

当前指标刷新按“月”处理分区：

- 历史月份默认视为稳定分区
- 当前月份可以重算并覆盖
- 如果只重算月内部分日期，会先读已有月分区再合并写回

同时，刷新会参考：

- `last_materialized_date`
- 指标声明的 `required_history_bars`

这保证了两件事：

- 不必每次全量重算全部历史
- 仍然可以为窗口型指标补足必要的历史数据

## 7. 当前已实现的指标能力

当前研究侧已经不只是“概念设计”，而是已有最小实现：

- 指标定义表和 repository
- 内置指标模块
- 指标脚本刷新入口
- Parquet 存储路径解析与分区读写
- 相关单元测试

换句话说，研究侧当前最稳定的部分不是回测，而是“指标定义 + 指标物化”。

## 8. 当前没有做的部分

这套方案当前还没有覆盖：

- DuckDB 查询层
- 宽表拼接工具
- 通用研究数据集抽象
- 因子评估结果落盘
- 选股结果落盘
- 回测结果与指标数据的一体化查询

这些能力要不要做，可以等回测主线真正落地后再收敛。

## 9. 当前结论

结合当前仓库状态，研究侧最合适的描述是：

> 标准层行情继续保留在 SQLite；研究侧指标通过 `indicator_definition` 管理，并按 `storage_key/year/month` 物化到 `data/indicators` 下的 Parquet 分区。

这是当前已经落地且最值得继续沿用的研究层存储边界。
