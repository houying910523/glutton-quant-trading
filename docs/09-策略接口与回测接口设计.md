# 策略接口与回测接口设计

## 1. 文档目的

这份文档合并了原来的“接口设计”和“详细设计”两份文档，只保留当前仓库真正需要的边界说明。

它回答两个问题：

1. 当前策略与回测应该怎么分边界
2. 下一步实现时，最小接口应该长什么样

## 2. 当前代码状态

当前与这条主线直接相关的代码状态是：

- `modules/indicators/` 已经实现了指标定义、内置指标、Parquet 存储和刷新
- `modules/backtest/` 仍是占位目录，`engine.py` 与 `analyzer.py` 目前为空
- 因此“指标计算”已经进入实现阶段，“策略运行时 / 回测引擎”仍处于设计先行阶段

这意味着本文件描述的是：

- 对现有指标层的承接方式
- 对后续策略与回测实现的收敛设计

而不是对一个已经存在的回测模块做事后说明。

## 3. 首版范围

首版仍然只服务于研究与回测闭环：

```text
标准层日线
-> 指标计算或读取
-> 策略生成信号
-> 回测解释信号
-> 输出回测结果
```

首版默认假设保持收敛：

- 频率：`1d`
- 市场示例：A 股
- 方向：`long_only`
- 信号类型：横截面选股 / 排序
- 调仓方式：固定频率调仓
- 首版持仓解释：`top_n + 等权`
- 首版成交假设：`next_open`

当前明确不做：

- 订单接口
- 账户与持仓状态机
- 风控插件系统
- 模拟盘与实盘执行接口

## 4. 当前边界划分

### 4.1 指标层负责什么

当前已经实现的 `Indicator` 体系负责：

- 声明计算所需列和历史窗口
- 基于日线历史计算指标值
- 把结果按 `storage_key` 物化到 Parquet

它不负责：

- 直接产出交易信号
- 解释持仓权重
- 运行完整回测

### 4.2 策略层负责什么

策略层首版只负责一件事：

> 在某个调仓日，对候选股票做过滤、排序和打分，输出可复现的信号顺序。

策略层不应该负责：

- 目标仓位分配
- 交易成本计算
- A 股规则校验
- 数据库或 HTTP 读取

### 4.3 回测层负责什么

回测层负责把“信号”翻译成“历史上的组合变化与收益结果”，包括：

- 生成调仓点
- 准备策略输入数据
- 校验信号合法性
- 解释为 `top_n + 等权` 目标持仓
- 计算 `next_open` 成交与收益
- 扣减手续费、滑点
- 输出汇总指标和明细产物

### 4.4 A 股规则放在哪里

A 股约束不能散落在策略里，必须挂在回测层规则对象中，例如：

- T+1
- 最小交易单位
- 涨跌停导致的无法成交

## 5. 为什么策略接口按“日期切片”设计

当前项目是日频横截面研究，不是逐 bar 事件驱动系统。

因此首版不做 `on_bar()` 风格接口，而是采用：

```text
给定某个交易日的候选标的数据切片
-> 返回该日信号列表
```

这样更符合当前代码基础：

- 标准层是日线表
- 指标层是按日计算
- 首版回测目标是固定频率调仓

## 6. 建议保留的最小接口

这里统一使用 Python 风格的 `snake_case` 命名。

### 6.1 策略接口

```python
class Strategy(ABC):
    def manifest(self) -> StrategyManifest: ...

    def validate_params(self, params: dict[str, object]) -> None: ...

    def generate_signals(self, input_data: StrategyInput) -> StrategyOutput: ...
```

关键约束：

- `generate_signals()` 是纯计算，不做外部 I/O
- 同一输入必须得到同一输出
- 策略只输出排序和解释，不输出持仓权重

### 6.2 策略输入

首版策略输入至少要能表达：

- `trade_date`
- 当日候选股票列表
- 当前 bar
- 必要的历史窗口
- 可选的预计算指标列
- 当前策略参数

也就是：

```text
当前 bar + 历史窗口 + 可选指标特征 + 参数
```

### 6.3 策略输出

首版信号记录至少包含：

- `instrument_id`
- `trade_date`
- `signal_side`
- `score`
- `reason`

其中：

- `signal_side` 首版只允许 `long` 或 `flat`
- `score` 用于稳定排序
- `reason` 只用于复盘和调试

### 6.4 回测接口

```python
class BacktestEngine(ABC):
    def run(self, request: BacktestRequest, strategy: Strategy) -> BacktestResult: ...
```

`BacktestRequest` 至少应包含：

- 回测日期区间
- 调仓频率
- 标的池定义
- `top_n`
- 费用和滑点参数
- 是否读取预计算指标

`BacktestResult` 至少应包含：

- 总收益
- 年化收益
- 最大回撤
- 交易次数
- 换手率
- 权益曲线
- 调仓明细或成交明细

## 7. 与当前指标层的衔接方式

首版策略层不需要重复发明一套“因子框架”，而应直接承接已有指标层：

1. 标准层日线来自 `daily_quote`
2. 预计算指标来自 `data/indicators/{storage_key}`
3. 策略决定是即时计算，还是消费已物化指标
4. 回测引擎负责把这些数据整理成某个调仓日可见的输入切片

这样可以避免：

- 在策略里重复写指标计算
- 在回测里直接耦合某个具体 `Indicator` 类

## 8. 当前推荐的实现顺序

结合仓库现状，后续应该按下面顺序推进：

1. 先补齐回测请求 / 结果模型
2. 再实现最小 `BacktestEngine.run()`
3. 先支持 `top_n + 等权 + next_open`
4. 最后再补策略样例和分析产物

原因很简单：

- 指标层已经可用
- 回测包还没有真实实现
- 现在最缺的是“如何把指标和日线真正接到策略与回测上”

## 9. 明确延后的能力

这轮设计明确延后：

- 组合优化器
- 风险预算框架
- 订单状态机
- 账户同步
- 模拟盘 / 实盘适配器
- 高频事件驱动 API

这些能力只有在首版回测闭环跑通之后再讨论，才不会过度设计。
