# 量化交易系统概览

## 1. 这到底是什么

量化交易系统不是一个“自动下单脚本”，而是一整套把市场数据转成交易决策、再把交易结果沉淀回系统的闭环。

如果只写一段策略代码，你最多得到一个“想法”。只有把下面这些能力补齐，你才拥有一个真正可运行的系统：

- 能稳定拿到市场数据
- 能验证策略是否在历史上有效
- 能控制仓位和风险
- 能把信号转换成真实订单
- 能追踪订单、持仓、资金和盈亏
- 能在出错时告警、停机、复盘

## 2. 为什么量化系统必须拆模块

因为“想法正确”和“交易能跑”是两回事。

一个最常见的失败路径是：

1. 策略信号看起来不错
2. 回测结果很好
3. 一到实盘就因为数据延迟、交易规则、仓位控制或订单状态处理不当而失真

所以系统必须拆成几个彼此独立的层：

- 数据层：回答“现在市场发生了什么”
- 研究层：回答“这个策略历史上是否有用”
- 决策层：回答“现在该买什么、买多少、何时卖”
- 执行层：回答“怎样把决策真正变成订单和成交”
- 保障层：回答“系统是否还活着、是否偏离了预期”

## 3. 一套完整系统的最小闭环

```text
市场数据 -> 数据清洗/存储 -> 策略信号 -> 仓位决策 -> 风险控制 -> 订单执行
-> 成交回报 -> 账户/持仓更新 -> 监控告警 -> 复盘分析
```

这个闭环里，任何一个环节缺失，系统都会失真：

- 没有数据治理：回测和实盘看到的市场不是同一个世界
- 没有风控：策略一旦犯错，亏损会被放大
- 没有订单状态管理：你根本不知道买没买到、买了多少
- 没有监控：系统挂了你都不知道

## 4. 从零基础需要先理解的四个运行阶段

### 4.1 研究

目标是快速试想法，不直接碰真实资金。

你会在这个阶段做：

- 选标的
- 做指标和因子
- 写策略逻辑
- 看收益、回撤、胜率、换手率

### 4.2 回测

目标是用历史数据模拟过去如果这样交易会发生什么。

回测不是“看收益曲线好不好看”，而是检验：

- 信号是否真的有用
- 仓位管理是否合理
- 交易成本是否会吞掉利润
- 风险是否超过你的承受能力

### 4.3 模拟盘

目标是在接近实盘的环境里，验证订单流、账户同步、监控和运行稳定性。

模拟盘经常暴露的问题不是策略，而是工程问题：

- 订单状态不同步
- 交易时间判断错误
- 资金冻结逻辑错误
- 程序重启后状态丢失

### 4.4 实盘

目标是让真实资金在受控条件下运行。

实盘的关键不是“自动化程度越高越好”，而是：

- 规则是否明确
- 风险是否可控
- 异常是否能及时发现
- 是否可以快速停机和复盘

## 5. `饕餮` 首版应该具备哪些能力

为了让系统可落地，首版只做最小可用能力，不做机构级复杂平台。

### 5.1 首版必须做

- 市场数据接入
- 数据标准化与存储
- 策略信号生成
- 基础回测引擎

这意味着 `饕餮` 首版本质上是一个“研究与回测系统”，还不是一个“可下单运行系统”。

### 5.2 延后做

- 组合构建
- 风险控制
- 订单管理与状态同步
- 账户与持仓状态
- 调度、日志、监控、告警

### 5.3 暂时不做

- 高频交易
- 超低延迟撮合
- 多账户清分
- 衍生品定价引擎
- 自动参数搜索平台
- 机构级权限和流程编排

## 6. 新手先记住这些术语

| 术语 | 白话解释 |
| --- | --- |
| 标的池 | 今天你允许策略考虑的股票集合 |
| 因子 | 用来解释或预测收益/风险的特征，例如动量、估值、波动率 |
| 信号 | 策略对某个标的发出的行动建议，例如买入、卖出、减仓 |
| 组合构建 | 决定每个标的最终分配多少仓位 |
| 风险控制 | 限制单票、行业、总仓位、回撤、成交异常等风险 |
| 回测 | 用历史数据模拟策略过去会怎么表现 |
| 模拟盘 | 接近实盘流程，但不动真实资金 |
| 订单管理 | 管理下单、撤单、部分成交、拒单等状态 |
| 适配器 | 把不同数据源、券商或交易所包装成统一接口的那层代码 |

## 7. `饕餮` 的首版定位

`饕餮` 不是要一上来就做成一个覆盖全市场、全品类、全频率的交易平台。

首版定位很明确：

- 面向个人开发者
- 低频优先
- 先解决研究和回测
- 暂不进入模拟盘和实盘执行
- 先把“数据到信号到回测报告”做扎实

这意味着接下来所有设计都要回答同一个问题：

> 这个设计是不是首版真的需要？

如果不是，就先不做。
